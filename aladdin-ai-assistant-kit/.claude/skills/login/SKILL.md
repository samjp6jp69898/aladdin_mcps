# agrabah-login — 登入 agrabah 後台（密碼不進對話紀錄）

## 何時使用

- 這是一份 kit 裡的第一個操作前，多半要先登入才能呼叫其他 MCP tool。
- 任何 MCP tool 回傳的錯誤訊息裡出現「請重新登入」「重新登入」這類訊號時，
  直接重跑本 skill，不需要問使用者原因——這是 hosted 模式下 JWT 過期的
  正常現象（15 分鐘過期是設計行為，不是 bug），登入態過期就直接重跑本
  skill 即可，跑完再重試原本失敗的那次操作。
- 使用者在對話裡提供 TOTP 動態驗證碼、要求你完成登入時（見下方「需要 TOTP
  驗證碼時」一節）。

## 怎麼呼叫（重要：指令字串必須逐字固定）

呼叫 Bash 工具時，指令字串必須**逐字**是：

```
bash .claude/skills/login/login.sh
```

**不要**在這行後面加任何參數（帳號、密碼、環境名稱、TOTP 驗證碼都不行）。
這支腳本被設計成 zero-args：所有動態資訊都由腳本自己去讀 `.env`／
`.mcp.json`，理由見 `../../settings.json` 裡的 `_securityNote`——這份 kit
的 Bash allowlist 只能安全地放行「指令內容從頭到尾固定不變」的呼叫，只要
你把任何動態值接在指令列後面，這條規則在設計上就不再安全（等於幫著把
Bearer token／密碼一起送出去的風險開了一個口）。

## 這支 skill 會做什麼

1. 從 kit 根目錄的 `.env` 讀出你的 agrabah 帳號密碼（純文字逐行解析，不會
   被印出來、不會出現在跟你的對話紀錄裡）。帳密是**一個後台一組、依環境分別
   讀**的：欄位名由 `.mcp.json` 的 server 別名機械推導——轉大寫、`-` 換成 `_`，
   加上 `_USER`／`_PASSWORD`。例如 `agrabah-admin-dev` 對應
   `AGRABAH_ADMIN_DEV_USER`／`AGRABAH_ADMIN_DEV_PASSWORD`，
   `agrabah-platform-dev-6t` 對應
   `AGRABAH_PLATFORM_DEV_6T_USER`／`AGRABAH_PLATFORM_DEV_6T_PASSWORD`。
   **沒有「填一組就通用」的共用欄位**：後台是「環境 × 平台產品」兩個維度
   （dev 的 PK 平台跟 dev 的 6T 平台是兩個不同站台、不同帳號），各自是互不
   相通的帳號名冊。某個環境沒填，就只有那個環境登不了，不影響其他環境。
2. 掃過 `.mcp.json` 裡每一筆已經填好真實 Bearer token 的環境（`agrabah-admin-dev`／
   `agrabah-admin-pre`／`agrabah-admin-evi`／`agrabah-platform`……你的 kit
   裡實際有哪幾筆，取決於工程師授權給你的範圍），對每一筆各自打一次該環境
   的 `POST /login`。**不需要你告訴它要登入哪個環境**——它會把 kit 裡每個
   已授權的環境都登入一輪，一次搞定；平常你只要在看到「需要重新登入」的
   訊號時重跑這支 skill 即可。
3. 逐筆回報結果：成功、失敗（附錯誤訊息）、或該環境需要 TOTP 驗證碼。

腳本執行完之後，把它印出來的每一行結果原樣告訴使用者。

## 需要 TOTP 驗證碼時

如果某個環境回報「需要 TOTP 動態驗證碼」，代表帳號密碼是對的，只是這個
環境的帳號另外開了兩步驟驗證：

1. 跟使用者說清楚：「這個環境需要你 App 上目前顯示的 6 位數動態驗證碼」，
   請他直接在對話裡告訴你。
2. 使用者提供驗證碼後，用 **Write 工具**（不是 Bash）把這組數字寫進固定
   檔案 `.claude/skills/login/.totp-code.tmp`（純文字，只放驗證碼本身，
   不要加其他內容）。
3. 寫完後，再次用 Bash 呼叫**同一個固定指令** `bash .claude/skills/login/login.sh`
   （還是 zero-args，不要把驗證碼接在指令列上）。腳本會自動讀到這個檔案、
   立刻刪除它、把驗證碼用在這一輪的登入嘗試上。

**這個驗證碼一定要當場問、當場用**：不要把它記在筆記或任何地方留著之後
用，也不要在使用者還沒提供前自己編一個或沿用之前用過的號碼——TOTP 驗證碼
通常只有約 30 秒的有效期，這是刻意設計成「每次都要當場輸入」，不是可以
預先存起來重複使用的東西。使用者中途覺得太麻煩想取消，直接停下來、不要
自己想辦法繞過登入去硬呼叫其他 tool。

**如果同一輪同時有好幾個環境都需要 TOTP**：dev/pre/evi 是各自獨立的帳號、
各自獨立的 TOTP 設定，一組驗證碼不可能同時滿足兩個環境。腳本一次只會
完整提示其中一個環境，其餘需要 TOTP 的環境只會印一句簡短提示。照腳本印出
的內容處理完第一個環境後，重跑一次 skill 再處理下一個，不要試著用同一組
驗證碼去滿足好幾個環境。

## 常見結果與你該怎麼回應使用者

- **登入成功**：告訴使用者登入完成，可以繼續原本要做的操作。
- **登入被拒絕（HTTP 401）**：這個狀態碼本身無法區分成因，腳本會列出幾種
  可能（帳密錯誤／Bearer token 失效／`.mcp.json` 網址設定有誤），把訊息
  原樣告訴使用者，請他先確認 `.env` 帳密無誤；如果確定沒問題，建議聯絡
  工程師，不要自己嘗試其他帳密組合。
- **登入嘗試過於頻繁（節流中）**：把腳本印出的「請於約 N 秒後再試」原樣
  告訴使用者，稍等再重跑，不要連續重試。
- **找不到 `.env`／`.mcp.json`，或帳密欄位是空的**：照腳本印出的訊息指引
  使用者，通常是還沒完成 `cp .env.example .env` 並填好帳密這一步
  （詳見 kit 根目錄 `README.md` 的安裝步驟）。
- **某個環境印出「略過：.env 裡找不到這個環境的帳號密碼」**：只有那一個
  環境沒填帳密，其他環境仍然照常登入了。把腳本指名的欄位名原樣告訴使用者
  請他補填即可；如果他根本沒有那個後台的帳號，請他聯絡工程師確認是不是不
  該拿到那個環境的 token，**不要建議他把別的環境的帳密填進去試**——各後台
  帳號名冊互不相通，試錯只會累積登入失敗次數（連續失敗會被鎖）。

## 這支 skill 絕對不會做的事（設計上的硬限制，不是遺漏）

- 不會把密碼印到任何輸出或對話裡。
- 不會把登入成功後拿到的 JWT／存取憑證印出來——那把憑證只留在 hosted
  server 端你這個 Bearer token 專屬的登入態容器裡，你（Claude）跟使用者都
  不需要、也看不到它的內容。
- 不會用 `-v`／`--trace` 之類會把 Authorization header 印到畫面上的 curl
  旗標。
- 不會把帳密或 Bearer token 放進任何指令列參數——全部透過 `curl --config -`
  從 stdin 餵給 curl，`ps aux` 看它的執行過程只會看到 `curl --config -`。

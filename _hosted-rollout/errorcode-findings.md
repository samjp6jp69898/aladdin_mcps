## 問題 1：abu 生成端具體形態

`rajah/services/common.rajah` 定義的 `AgrabahErrorCodeEnum` 在 abu 生成端是一個**標準 TypeScript numeric enum**（`export enum ...`，不是 `const enum`、不是 plain object、不是型別別名）。

- rajah source：`rajah/services/common.rajah:3`（`enum AgrabahErrorCodeEnum {`）、`:7`（`loginRequired = 103`）。
- admin 生成端：`abu/admin/src/generated/remote.gen.ts:11777`（`export enum AgrabahErrorCodeEnum {`）、`:11783`（`loginRequired = 103,`）、`:11936`（`gameVendorGameNotExists = 303,`）。（以上為本次 `grep -n` 實測行號，非沿用舊行號。）
- platform 生成端：`abu/platform/src/generated/remote.gen.ts:19702`、`:19708`、`:19861`，同上三個成員值相同。
- 因為是普通 `enum`（非 `const enum`），TypeScript 編譯後會同時產生**正向映射**（`AgrabahErrorCodeEnum.loginRequired === 103`）與**反向映射**（`AgrabahErrorCodeEnum[103] === 'loginRequired'`）。此行為已用真實 `bun run` 實測驗證，見問題 4。

## 問題 2：admin 端與 platform 端生成檔是否同一份

**不是同一份檔案，是兩個獨立生成的檔案**（不同 repo 路徑、不同 module graph、執行期是兩個不同的 JS enum object，沒有共用 reference）。但這個特定 enum 的**內容**恰好逐字相同：

```
awk '/^export enum AgrabahErrorCodeEnum/,/^}/' abu/admin/.../remote.gen.ts   → 1873 行
awk '/^export enum AgrabahErrorCodeEnum/,/^}/' abu/platform/.../remote.gen.ts → 1873 行
diff 兩者 → 完全一致（無差異）
```

原因是 `common.rajah:1` 檔頭明寫「`WARN : this file will include in ALL projects`」——`AgrabahErrorCodeEnum` 源自這份**跨專案共用**的 rajah 檔，admin 與 platform 的 `project.json` 各自把它 generate 進自己的 `remote.gen.ts`，兩邊生出來的內容因此一致。

**不能因此假設「兩邊 error enum 永遠一樣」**：`mcps/README.md:69` 已提醒過「兩邊常常同名概念但是完全不同的 model」（業務 model 如 `GameVendorEssential` 為例）；`AgrabahErrorCodeEnum` 這個特例之所以相同，純粹是因為它來自 `common.rajah` 而非各專案自己的 `.rajah`。若之後 D10 要用到的是其他 error/enum 定義且來源不是 `common.rajah`，仍須重新逐一確認、不可比照辦理。

用真實反例佐證這個提醒不是空泛警告：`rajah/services/scheduler.rajah:1` 定義的 `SchedulerTypeEnum`，`abu/admin/rajah/project.json` 的 `rajahClientFilenames` 有納入 `scheduler`、`abu/platform/rajah/project.json` 沒有——實測 `grep -n "enum SchedulerTypeEnum" abu/admin/src/generated/remote.gen.ts` 命中 `:6416`，同樣指令打在 `abu/platform/src/generated/remote.gen.ts` 完全無命中。可見「只在單邊生成端存在、另一邊查不到」是真實會發生的情況，不是理論上的可能性。

實作面結論：**admin 的 MCP 要 import admin 生成端的 enum，platform 的 MCP 要 import platform 生成端的 enum**，各自獨立、不要為了「反正內容一樣」就跨專案共用一份 import 路徑（兩個 MCP server 本來就是各自獨立的 process/package，也沒有機制能共用同一個模組實例）。

## 問題 3：MCP 能否直接絕對路徑 import 這個定義

**可行，已實測**。用跟 `session.ts:19` 完全一樣的絕對路徑 import 手法，寫了兩支探測腳本（放在 session scratchpad，未進 repo）：

```ts
import { AgrabahErrorCodeEnum } from '/Users/user/aladdin/abu/admin/src/generated/remote.gen.ts';
```

實測輸出（`bun run`，admin 端）：
```
typeof AgrabahErrorCodeEnum: object
forward loginRequired -> 103
reverse 103 -> loginRequired
reverse 204 (userNotExists, 真實打到的錯誤碼) -> userNotExists
reverse 303 -> gameVendorGameNotExists
reverse unknown code 999999 -> undefined
```
（`time` 量測整支腳本含 bun 啟動 0.122s，無例外、無循環依賴報錯。）

platform 端同樣手法（`import ... from '/Users/user/aladdin/abu/platform/src/generated/remote.gen.ts'`）也成功，`reverse 103 -> loginRequired`、`reverse 303 -> gameVendorGameNotExists`。

補充事實：
- `AgrabahErrorCodeEnum` 只存在於 `remote.gen.ts`（19176 行），**不在** `types.gen.js`（5137 行，grep 無命中）。要 import 它就得載入 `remote.gen.ts` 整份檔案——但這不是額外成本，因為 `session.ts:19` 早就已經在 import 同一個檔案裡的 `Remote` class，MCP process 本來就會載入這份檔案一次。
- 未知錯誤碼反查會得到 `undefined`（不會拋例外），這點在 H11 實作時要處理：反查不到時保留原始數字、標示「未知碼」，而不是讓程式在 `undefined.something` 上炸掉。
- 沒有觀察到循環依賴問題：`remote.gen.ts:1` 檔頭是 `// THIS FILE IS GENERATED BY JASMINE, IF YOU WANT TO MODIFY THIS FILE, PLEASE MODIFY SOURCE RAJAH FILE INSTEAD`，`:3-4` import 的是 `genie/client` 的 `ServiceResult`/`ClientServiceBase`/`ClientGroupBase`/`HeaderHandler`/`BaseUrlHandler`，跟 `session.ts` 現有的 import 路徑一致，沒有新增依賴方向。

**結論：可以直接 import，不需要替代方案**（原 task 描述預留的「MCP 內產生對照表」備案不需要採用）。

## 問題 4：後端錯誤名稱是否可從回應中取得

**不行——後端只回數字，不回名稱**。名稱必須靠 MCP 端用生成 enum 對數字做反向映射反查。

結構性證據：
- `GenieResponse` 的欄位定義（`genie/src/common/types.gen.d.ts:3-19`，`IGenieResponse` 介面 `:3-7`）：
  ```ts
  export interface IGenieResponse {
      errorCode?: (number|null);
      message?: (string|null);
      data?: (Uint8Array|null);
  }
  ```
  只有 `errorCode`（數字）、`message`（字串）、`data`（bytes，需要再拆一層 protobuf decode 才是業務資料本體）。沒有任何「錯誤名稱」欄位。
- `session.ts` 的 `withAutoRelogin` 回傳型別（`session.ts:74-76`）與 `login()` 的失敗分支（`session.ts:56`）同樣只暴露 `errorCode`/`message`。

真實 dev 呼叫樣本（本次實際打 `mcp__agrabah-admin__agrabah_admin_login` 工具，故意帶不存在的帳號觸發失敗）：
```json
// 輸入：identifier="h10_probe_nonexistent_user_xyz", password="wrong-password-h10-probe"
{
  "success": false,
  "errorCode": 204,
  "message": ""
}
```
`errorCode: 204` 反查 `AgrabahErrorCodeEnum[204]` → `userNotExists`（與 `common.rajah` 的 `userNotExists = 204` 一致，肉眼可在 grep common.rajah 的輸出裡確認）。**值得注意的額外發現**：這次真實回應的 `message` 是空字串——代表 D10「透傳錯誤名稱」不能指望 `message` 欄位有內容可用，唯一可靠的診斷來源就是 `errorCode` 的 enum 反查結果。

機制結論：D10「把後端錯誤名稱原樣透傳給 agent」的唯一可行實作是——
```ts
const name = AgrabahErrorCodeEnum[r.errorCode]; // number → string，反查不到時是 undefined
return asTextResult({ success: false, errorCode: r.errorCode, errorName: name ?? '(未知錯誤碼)', message: r.message });
```
不是去 `GenieResponse`/`ServiceResult` 物件裡找一個原本就不存在的「name」欄位。

本次重新 `grep -n "loginRequired" rajah/services/common.rajah` 確認 `loginRequired = 103` **確實在第 7 行**（未漂移），值 `103` 正確。**該註解與常數目前都正確，未漂移**。

## 對 H11 的具體建議（供下一 task 引用，非本 task 交付物）

1. `const.ts` 撤掉 `LOGIN_REQUIRED_ERROR_CODE` 這個裸數字常數，改成兩個 server 各自的 `session.ts` 直接 `import { AgrabahErrorCodeEnum } from '<abu/admin 或 abu/platform>/src/generated/remote.gen.ts'`，`withAutoRelogin` 判斷未登入改用 `r.errorCode === AgrabahErrorCodeEnum.loginRequired`。
2. tool 回傳給 agent 的錯誤內容統一加上 `errorName: AgrabahErrorCodeEnum[r.errorCode] ?? undefined`，反查不到時保留原始數字並如實標示「未知錯誤碼」，不得讓 undefined 流入回應文案造成誤導。
3. 兩個 server 各自 import 各自專案的生成檔（問題 2 的結論），不要建立跨專案共用模組。
